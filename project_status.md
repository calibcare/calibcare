## Schema summary (5 tables)

- `equipment` — one row per physical instrument
- `equipment_capability` — one row per measurement purpose an instrument supports (this is what the DSS will query)
- `calibration_history` — append-only calibration events per equipment
- `users` — logins/roles + LINE user id for reminders
- `notification_log` — audit trail of LINE reminders sent

## Key decisions made (so future work stays consistent)

- Calibration dates live on `equipment`, not `equipment_capability` — confirmed from the source data that all capability rows under one instrument share the same last/next calibration date (except 3 groups where they genuinely differed, kept as separate history rows).
- `equipment.status` is a normalized ENUM (`active`/`decommissioned`/`sent_for_calibration`); the original free-text Thai status (which encodes dates/reasons inline) is preserved in `status_note` so nothing is lost.
- `equipment.manufacturer` and `equipment.category` are reserved nullable columns — the source Excel doesn't track these yet, but the project spec calls for them (Objective 1, dashboard "by manufacturer/category").
- Serial numbers are NOT enforced unique — 4 real duplicates exist in the source data (calibration weight sets like `M1801082N(ID4)-1KG` appear twice), so it's a plain index, not a unique key.

## Decision Support System — how it works

- **Endpoint**: `POST /api/dss/match` — body `{ requirements: [{ measurement_purpose, min, max, unit }] }`.
- **Comparison field**: requirements are checked against `equipment_capability.measurement_range` (the instrument's own capability), not `product_operating_range`. Confirmed against real data: the spec's example "Pressure 0–8 bar" only makes sense checked against the Gas Flow Analyzer VT650's `measurement_range` (-0.8 to 10 bar) — its `product_operating_range` for Pressure is 0-0.14 bar, which wouldn't fit.
- **Range parsing** (`rangeParser.js`): handles the source data's inconsistent formats — `"35-160kVp"` (hyphen glued to unit), `"-0.8 to 10 bar"` (genuine negative + "to"), `"0 to ±200 slpm"` (symmetric ± range). Key heuristic: a hyphen directly between two digits is a range separator, not a minus sign (real minus signs in this dataset are followed by "to").
- **Unit safety**: if the requirement's unit and the equipment's parsed unit don't match (e.g. `l/min` vs `slpm`, `psi` vs `bar`), the requirement is marked failed with an explicit "unit mismatch" reason rather than silently comparing incompatible numbers.
- **Ranking**: among suitable equipment, results are sorted by tightest-fitting range first (smallest total margin over the requested range) so the "most suitable" recommendation isn't just the first wide-range match.
- **Verified live**: ran the spec's exact example (Flow 0–180 slpm, Pressure 0–8 bar, Oxygen 21–100%) against the real seeded DB — correctly returned all 7 active VT650 units as suitable, and correctly rejected the CITREX H5 (unit mismatch on Flow, missing Pressure/Oxygen capability) and all Pressure Calibrators (psi vs bar unit mismatch).

## Auth — how it works

- `POST /api/auth/register` — `{full_name, email, password, role?, line_user_id?}` → hashes password with bcrypt, inserts into `users`, returns a JWT + public user object (password_hash never returned).
- `POST /api/auth/login` — `{email, password}` → verifies password, returns the same JWT shape.
- JWT is sent as `Authorization: Bearer <token>` on every subsequent request; `requireAuth` middleware verifies it and attaches `req.user`. `requireRole('admin')` further restricts a route to specific roles.
- `/api/dss/*` and `/api/reminders/*` are now behind `requireAuth`. `/api/auth/*` itself is intentionally public (you can't log in to a login route).
- A test account exists in the live DB for convenience: `admin@mcems.local` / `correct-horse-battery-staple`, role `admin`, with a placeholder (fake) `line_user_id` so reminder dry-runs have a recipient to test with. Delete or change this before this ever goes near production.

## LINE reminder scheduler — how it works

- `reminderService.checkAndSendReminders(db, lineClient, today?)` is the pure logic: finds each active equipment's most recent calibration record, computes days-until-due, and buckets it into `overdue` / `due` / `7_days` / `14_days` / `30_days` (using `<=` thresholds so a missed cron run still catches up next time instead of silently skipping).
- Before sending, it checks `notification_log` for an existing `(calibration_id, bucket)` row — if that exact reminder was already sent, it's skipped, so the same threshold doesn't fire every day for 30 days straight.
- Recipients = every user with a non-null `line_user_id` (there's no per-equipment "responsible engineer" link in the real data — `responsible_person` in the sheet was always "Service admin" — so for now it's a broadcast to all subscribed users via LINE's multicast API).
- `lineClient.js`: if `LINE_CHANNEL_ACCESS_TOKEN` is unset, returns a dry-run client that only logs what it would send. **Dry-run sends are deliberately never written to `notification_log`** — a bug caught and fixed during this session: logging a dry-run as "sent" would have permanently blocked the real reminder once a real LINE token gets configured, since the dedup check only looks at row existence, not status.
- `scheduler.js` wires this into `node-cron` on `REMINDER_CRON` (default `0 8 * * *`, 8am daily), started automatically when `server.js` boots.
- `POST /api/reminders/run` (admin-only) manually triggers the same check on demand — used to test/demo without waiting for the actual clock time.
- Verified live against real data: correctly found a genuinely overdue instrument (Electrical Safety Analyzer, 24 days overdue) and 18 more due within 30 days, all in dry-run since no real LINE OA is configured yet.

## Equipment CRUD API — how it works

- `GET /api/equipment?q=&status=&limit=&offset=` — search by name/model/serial_number/location substring, optional status filter, paginated (default limit 50, capped at 200). Returns `{total, limit, offset, equipment}`.
- `GET /api/equipment/:id` — one equipment record plus its `capabilities` array and `latest_calibration` (most recent `calibration_history` row by date, or `null` if none logged yet).
- `POST /api/equipment` — registers new equipment. Requires `name` + `serial_number`. `equipment_no` (the "เลขที่" register number) is auto-assigned as `MAX(existing) + 1` — mirrors how the source spreadsheet numbers equipment.
- `PUT /api/equipment/:id` — partial update; only fields present in the request body are changed, everything else stays as-is.
- `DELETE /api/equipment/:id` — deletes equipment; its capabilities and calibration history cascade-delete automatically (`ON DELETE CASCADE`, already in `schema.sql`).
- `POST/PUT/DELETE /api/equipment/:id/capabilities[/:capabilityId]` — manage an equipment's measurement capabilities (the rows the DSS matches against).
- **Role gating**: all reads require any logged-in user; all writes (`POST`/`PUT`/`DELETE`, on both equipment and capabilities) require role `admin` or `engineer` — QA/manager accounts can view but not edit, matching who the spec lists as actually managing equipment records.
- **Verified live end-to-end**: created a test instrument, added a capability to it, fetched it back (capability included), updated its status, deleted the capability, deleted the equipment, and confirmed the total count returned to exactly 163 — nothing left behind. Also confirmed invalid status values are rejected (400) and unauthenticated requests are blocked (401).

## LINE webhook + account linking — how it works

- **Why a webhook at all**: our system can only send a LINE message to someone once we know their real LINE user ID, and there's no way to look that up ourselves — LINE tells us via a webhook call the moment someone follows the Official Account or messages it. So two new pieces work together: a way for a logged-in MCEMS user to prove "this LINE account is mine," and a receiver for LINE's calls.
- **The linking flow**: `POST /api/line/link-code` (logged in) generates a random 6-digit code tied to that user's `user_id`, held in memory for 10 minutes (`linkCodeStore.js` — deliberately not a DB table; losing a pending code on server restart just means requesting a new one, not worth a migration). The user adds the OA as a friend and sends that code as a LINE message. `POST /api/line/webhook` receives it, matches the code back to the waiting `user_id`, and writes the sender's real LINE user ID into `users.line_user_id` — then replies on LINE confirming success.
- **Webhook security**: `POST /api/line/webhook` is deliberately **not** behind our `requireAuth` (LINE's servers can't send our JWT) — instead every request must carry a valid `x-line-signature` header, which is an HMAC-SHA256 of the exact raw request body, keyed with your channel secret. `lineWebhookService.verifySignature()` recomputes it and does a constant-time comparison; anything that doesn't match (wrong secret, tampered body, no signature at all) gets `401`'d before any event is processed. This required one plumbing change in `server.js`: `express.json()` normally throws away the raw bytes after parsing, so it's now configured with a `verify` callback that stashes them on `req.rawBody` for the signature check.
- **A real bug caught before it shipped**: `linkCodeStore.consumeLinkCode()` trimmed whitespace when *looking up* a code but deleted the map entry using the untrimmed key — so a code sent with stray spaces (very plausible from a phone keyboard) would validate correctly but never actually get removed, breaking the "single-use" guarantee and leaving a valid code sitting around past its intended one-time use. Caught by writing a test for exactly that case before trusting the code, not after.
- **Verified live, not just unit-tested**: temporarily set a real-format `LINE_CHANNEL_SECRET`, requested a real linking code as the logged-in demo admin, then simulated an actual signed LINE webhook call (Python script computing the real HMAC-SHA256 the way LINE does) — confirmed the admin's `line_user_id` in the live database actually changed to the simulated LINE user ID. Also confirmed a forged/wrong signature gets `401`'d. Cleaned up afterward (restored the demo account's placeholder ID, reverted the test secret) so no test artifacts were left in the "real" state.
- **Frontend**: `RemindersPage.jsx` now has a "Connect your LINE account" card — click "Get linking code," see the 6-digit code plus a live countdown, with an "Add as friend" link that becomes clickable once `LINE_OA_BASIC_ID` is configured. Verified live in a headless browser (screenshot confirmed).

## Calibration history UI — how it works

- **Endpoints** (all in `equipment.js`, same file/pattern as capabilities): `GET /api/equipment/:id/calibrations` (any logged-in role, most-recent-first), `POST` (admin/engineer, requires `calibration_date`), `PUT /:calibrationId` (partial update, for correcting mis-entered records), `DELETE /:calibrationId`.

Actual file upload (accepting a PDF, storing it, serving it back) is a separate, not-yet-built feature — the field just lets someone note where the certificate lives for now, and the input is explicitly labeled so it doesn't imply upload functionality that doesn't exist.

## Date display bug — found and fixed during this session

- **What was wrong**: every date shown anywhere in the app — the dashboard's due/overdue tables, the equipment detail page's "last calibrated / next due" line, and the text of LINE reminder messages — was **one day earlier** than what was actually stored in the database. E.g. the database genuinely had `2026-08-11` for one instrument's next due date, but the API reported `2026-08-10`.
- **Root cause**: the `mysql2` driver, by default, converts SQL `DATE` columns into JavaScript `Date` objects representing local midnight on the server. When Express serializes a response with `res.json()`, `Date` objects get converted to UTC via `.toISOString()` — and since this server's system timezone (ICT, UTC+7) is ahead of UTC, local midnight of a given date lands on 17:00 (5pm) the *previous* day once expressed in UTC. Every place in the frontend that then took just the first 10 characters of that string (to get "just the date") was silently reading the wrong day.
- **How it was caught**: while testing the new calibration history feature, a record entered as `2026-07-15` came back from the API as `"2026-07-14T17:00:00.000Z"`. Rather than assume that was expected ISO-format noise, the raw stored value was checked directly in MySQL (`2026-07-15`, correct) — confirming the bug was in the serialization layer, not the data.
- **The fix**: `db.js`'s connection pool now sets `dateStrings: true`, which tells `mysql2` to return `DATE`/`DATETIME`/`TIMESTAMP` columns as plain strings exactly as MySQL stores them (e.g. `"2026-08-11"`), never converting to a `Date` object at all — eliminating this entire class of bug at the source in one place, rather than patching every individual display site.
- **Verified the fix**, not just the symptom: re-checked the same previously-broken values (equipment #17's calibration date, the dashboard's due-soon row for serial `5040061`) and confirmed both now match the real database values exactly (`2026-05-19` and `2026-08-11` respectively, not the previously-shown `05-18`/`08-10`). This also retroactively corrects a value shown earlier in this very session's equipment-detail screenshot, which had displayed the wrong (shifted) date without anyone noticing at the time.
